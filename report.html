Why the middle branch is the whole problem

A delete or modify row gives the order's new state. It never says which price level that order is currently sitting on. Without live_orders remembering it, a modify that moves an order between prices would subtract quantity from the wrong level — and every row after it would be silently wrong.

SortedDict O(log n) The book needs both keyed access (“quantity at price X”, for applying an update) and ordered access (“best five”, for the output). A plain dict gives only the first; a heap only the second. This gives both, and the top-5 read is O(5).

The target, and its horizon

y(t) = ( mid(t + h) − mid(t) ) / 5 The target is the change, not the level. mid is the average of best bid and best ask; the divisor is the tick size, so y is in ticks. The forward value is the mid prevailing at t + h — the last update at or before it, since updates arrive irregularly.

The ten features, calculated

Every number below comes from one real row: bids 10005×26, 10000×4, 9995×31, 9990×46, 9985×44 · asks 10010×4, 10015×9, 10020×20, 10025×48, 10030×45.

spread_ticks
How much room there is to move.
(ap0 − bp0) / tick = (10010 − 10005) / 5 = 1.0
One tick wide — the tightest the book gets, and where it sits most of the day.
imbalance_touch
Relative size of the two front queues. The single most informative number in a one-tick book.
(bq0 − aq0) / (bq0 + aq0) = (26 − 4) / (26 + 4) = 22 / 30 = +0.733
Runs −1 (all sellers) to +1 (all buyers). Here: heavily bid.
touch_share_bid
What fraction of the side's five-level depth sits at the front.
bq0 / (bq0+bq1+…+bq4) = 26 / (26+4+31+46+44) = 26 / 151 = 0.172
Only 17% at the touch — plenty of depth behind it.
touch_share_ask
Same for the sell side.
aq0 / (aq0+aq1+…+aq4) = 4 / (4+9+20+48+45) = 4 / 126 = 0.032
A very thin front queue — 3% of ask depth. Easily cleared, which is how the ask stepped up.
mid_change_1s / 5s / 30s
Realised drift, against the mid prevailing a window ago — not a fixed number of rows back.
(mid(t) − mid(t−30s)) / tick = (10007.5 − 10002.5) / 5 = +1.0 (30s window) 1s and 5s windows: 0.0
Up a full tick over 30s, flat over the last 5. All three coefficients are negative — short-horizon mean reversion.
ofi_1s / 5s / 30s
Net pressure at the touch. Buying interest arriving minus selling interest arriving, summed over the window. A price move counts the whole old queue as leaving and the whole new one as arriving.
per event, bid side: price same → new size − old size price up → + new size price down → − old size (ask side mirrored, then subtracted) sum over window ÷ mean touch size 30s: +1.815 1s: −0.033
Sustained buy pressure over 30s, flat over the last second. Dividing by typical touch size keeps it comparable between quiet and busy periods.
Twelve more were built, measured, deleted

Depth-weighted imbalance, log depth ratio, rolling volatility / event rate / cancel ratio at each window — all had coefficients near zero and five flipped sign between folds. The size-weighted micro-price offset went too, for the opposite reason: it correlated with touch imbalance at 0.99, and carrying both cost stability while buying 0.001 of out-of-sample IC.

One feature was removed on this evidence

An earlier version also carried the size-weighted micro-price offset. It is algebraically (spread / 2) × imbalance, and since the spread is one tick for most of the session the two correlated at 0.99, with VIFs above 50. The fit responded exactly as collinearity predicts: it gave imbalance +0.12 and the micro-price −0.06, two large opposing coefficients that partly cancelled and were impossible to read on their own.

Dropping it cost 0.001 of out-of-sample IC — and sign accuracy went up. Imbalance's coefficient settled to a single clean +0.063, and the regression's condition number fell from 18.7 to 5.15. What is left is mild collinearity that ridge absorbs comfortably.

It also explains an oddity below: ofi correlates with the target at only 0.02–0.03 on its own, yet is strongly significant in the fit. It adds information conditional on imbalance rather than on its own.

The model is a multiple linear regression

Ten features, one continuous target, fitted with a least-squares linear model. The production fit adds an L2 (ridge) penalty because the features are collinear; alongside it an unpenalised OLS is fitted purely to read off standard errors and confidence intervals, which a penalised fit cannot give.

# the signal — penalised, used for prediction Pipeline([("scale", StandardScaler()), ("ridge", RidgeCV(alphas=(0.1, 1, 10, 100, 1000)))]) # the diagnostic — unpenalised, used for inference standardised = (features - features.mean()) / features.std() sm.OLS(target, sm.add_constant(standardised)).fit().summary()

The number that validates the subsampling

Durbin–Watson = 2.016. A value of 2 means no autocorrelation in the residuals — which is exactly what the thinning was for. Fitted on every row with overlapping targets, this would have come out near zero and every standard error above would be badly understated. It is the empirical proof that the sampling choice was the right one.

Kurtosis is 17.8, so the residuals are fat-tailed. The intervals above assume normality and are best read as indicative; robust standard errors would widen them somewhat without changing which features matter.

Predicted against realised

The obvious chart — a point per row, predicted on one axis and realised on the other — does not work here. The mid moves in half-tick steps, so realised values take only 13 distinct levels, and 85.6% of rows sit exactly on zero. All 22,361 points would collapse onto thirteen horizontal stripes with almost everything on one of them, which says nothing about the fit.

Binning by prediction and averaging the realised move inside each bin recovers the relationship. Twenty equal-count bins below, each about 1,118 rows, with 95% intervals:

Dots follow the dashed line closely, so the model is well calibrated: when it says +0.10 ticks, the realised average is close to +0.10. A line fitted through the bins has slope 1.16 — slightly above 1, meaning the model marginally under-states magnitude, which matches the decile view. Predictions span only −0.46 to +0.35 ticks: this is a small, consistent tilt, never a confident call.

Mean realised move in ticks per decile of predicted move. Monotone across all ten groups.

Why this matters more than R². It tests ranking, not magnitude. The model systematically under-predicts size — its most bullish decile forecasts 0.13 ticks and realises 0.15 — but it puts the rows in the right order, and order is what a trading signal is used for: you act on the strongest conviction, not on the literal number. A model with a poor R² but a clean monotone profile is still useful; a model with a decent R² and a jagged profile usually is not.

The captured 0.072 ticks against a ~0.5 tick crossing cost is the honest limit: a real predictive relationship, not a strategy.
